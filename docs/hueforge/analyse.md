## 1. Comment fait Snapmaker Orca

### 1.1 Modèle de données [V-code]

- Un point de changement est un `CustomGCode::Item { print_z, type, extruder, color, extra }` (`O/libslic3r/CustomGCode.hpp:24-46`).
- Les types possibles sont `ColorChange`, `PausePrint`, `ToolChange`, `Template`, `Custom` et `Unknown` (`CustomGCode.hpp:14-22`). Dans le XML, ils sont codés en entiers de 0 à 5.
- La liste d'une plaque est un `Info { mode, gcodes }`. `mode` vaut `SingleExtruder`, `MultiAsSingle` ou `MultiExtruder` (`CustomGCode.hpp:67-92`).
- Le modèle garde une liste par plaque : `Model::plates_custom_gcodes` (`O/libslic3r/Model.hpp:1561-1566`).
- `extruder` est un numéro de filament à partir de 1. Il peut viser une **tête virtuelle**, c'est-à-dire un filament mixte, et pas seulement une tête physique (`CustomGCode.hpp:123-126`, `CustomGCode.cpp:62-73`).

### 1.2 Interface : la barre de couches de l'aperçu (IMSlider) [V-code]

- La barre de couches est un ascenseur ImGui (`O/slic3r/GUI/IMSlider.cpp`). Les repères (ticks) sont des **index de couches**. À l'export, chaque repère est converti en `print_z`, la hauteur du haut de cette couche : `GetTicksValues` (`IMSlider.cpp:212-227`). À l'import, la hauteur est ramenée à la couche par `get_tick_from_value` (`IMSlider.cpp:240-245`, `1606+`).
- Menu « + » sur une couche (`render_add_menu`, `IMSlider.cpp:1343-1395`) :
  - Add Pause ;
  - Add Custom G-code (fenêtre de saisie, `1158-1220`) ;
  - Add Custom Template, seulement si `template_custom_gcode` n'est pas vide ;
  - Jump to Layer ;
  - un sous-menu **Change Filament** (Filament 1…N, avec la pastille de couleur), seulement s'il y a plus d'un filament.
- Menu d'édition d'un repère existant (`IMSlider.cpp:1401-1440`) : supprimer la pause, modifier ou supprimer le G-code perso, changer le filament cible ou supprimer le changement.
- Le changement de filament n'est proposé que si **tous les objets de la plaque utilisent le même filament** : `can_change_color` (`O/slic3r/GUI/GUI_Preview.cpp:490-533`). Sinon, les repères `ToolChange` sont effacés (`IMSlider.cpp:247-253`). Il n'est pas proposé non plus en impression objet par objet ni en mode vase (`IMSlider.cpp:320`, `336`).
- Le message d'une pause n'est **pas saisi** dans cette version (« BBS do not set pause extra message », `O/slic3r/GUI/TickCode.cpp:103-108`).
- Dans l'aperçu, la vue « Color Print » colore par plage de hauteur à partir de ces repères (`O/slic3r/GUI/GCodeViewer.cpp:1038`, `4660-4670`, `5146`).

### 1.3 Stockage dans le 3MF [V-code]

- Le fichier est `Metadata/custom_gcode_per_layer.xml` (`O/libslic3r/Format/bbs_3mf.cpp:176`).
- Écriture (`bbs_3mf.cpp:8012-8066`) : `<custom_gcodes_per_layer><plate><plate_info id="1"/><layer top_z="…" type="2" extruder="2" color="#…" extra="…" gcode="tool_change"/>…<mode value="MultiAsSingle"/></plate>…`
- Lecture (`bbs_3mf.cpp:3108-3190`) : un fichier sans `<plate>` est attribué à la plaque 1. L'ancien format Prusa sans `type` est accepté, avec `gcode="M600"/"M601"/"tool_change"`.
- Le fichier n'est lu que si la configuration est chargée (`!dont_load_config`, `bbs_3mf.cpp:1791`, `1876-1878`).

### 1.4 Prise en compte par le CLI [V-code + V-essai]

Le CLI offre deux voies, et elles donnent le **même G-code** [V-essai, `json` = `xml` dans `resultats.txt`] :

1. **Le 3MF d'entrée.** Un `.3mf` placé en premier est chargé avec `LoadConfig` (`O/Snapmaker_Orca.cpp:1396-1413`), donc son `custom_gcode_per_layer.xml` est lu.
2. **L'option `--load-custom-gcodes <fichier.json>`** (`O/libslic3r/PrintConfig.cpp:8709-8713`). La clé `load_custom_gcodes` devient `--load-custom-gcodes` (`O/libslic3r/Config.cpp:247-251`).
   - Le JSON est lu par `Info::from_json` : `{"mode":"MultiAsSingle","gcodes":[{"type":"ToolChange","print_z":0.48,"extruder":2,"color":"#808080","extra":""}]}` (`Snapmaker_Orca.cpp:1659-1690`, `CustomGCode.hpp:47-64`, `94-110`).
   - Il est injecté dans le modèle **à la place** des repères du 3MF (`Snapmaker_Orca.cpp:2936-2939`).
   - Les entrées `Custom` sont retirées si `skip_modified_gcodes` est actif (`2949-2960`).

### 1.5 Génération du G-code [V-code]

**ToolChange (changement de tête)** : c'est le seul type qui change réellement de couleur sur une machine multi-têtes.

- La bascule n'est appliquée que si le mode est `MultiAsSingle`, qu'il y a plus d'un filament **et que la plaque n'imprime qu'avec un seul extrudeur** (`O/libslic3r/GCode/ToolOrdering.cpp:451-464`).
- La bascule remplace l'extrudeur de toutes les couches dont le haut est ≥ `print_z` (`ToolOrdering.cpp:713-735`). La cible passe par `resolve_mixed`, ce qui permet de viser une tête virtuelle.
- Le G-code de changement est celui du profil, `change_filament_gcode` (`O/libslic3r/GCode.cpp:8755-8762`).
- Le filament visé est compté comme utilisé, ce qui compte pour la tour de purge (`O/libslic3r/Print.cpp:951-967`).
- Une modification des ToolChange invalide la tour de purge et l'export, une modification des autres types seulement l'export (`O/libslic3r/PrintApply.cpp:1484-1497`).

**PausePrint, Template, Custom**

- Ils sont rattachés à la couche **la plus proche**, selon la règle du point milieu (`ToolOrdering.cpp:1289-1351`).
- Ils sont émis au début de la couche (`GCode.cpp:5043-5046`), avec ces sorties :
  - Pause : `;PAUSE_PRINT` puis `machine_pause_gcode` (`GCode.cpp:4515-4522`). Le message (`extra`) **n'est pas écrit**, la ligne `M117` est commentée (`4519-4521`).
  - Template : `;CUSTOM_GCODE` puis `template_custom_gcode` (`4526-4527`).
  - Custom : `;CUSTOM_GCODE` puis le texte `extra` (`4528-4529`).
- Ces étiquettes sont celles de `GCodeProcessor` (`O/libslic3r/GCode/GCodeProcessor.cpp:83-85`, `2065-2075`).

**ColorChange (M600 « à la Prusa »)** : dans ce fork BBS, ce type est **neutralisé**.

- Tout le bloc qui émettait `color_change_gcode` est sous `#if 0` (`GCode.cpp:4483-4513`).
- La clé `color_change_gcode` n'existe même pas dans `PrintConfig.cpp` (aucune occurrence).
- Un `ColorChange` ne produit donc qu'une étiquette `;CUSTOM_GCODE` suivie d'un `extra` vide (`4524-4530`).
- **Conséquence** : sur la U1, « changer de couleur à une hauteur » veut dire soit un `ToolChange` (changement de tête), soit une `PausePrint` (M600 → PAUSE, cf. 1.7).

**Impression objet par objet** : rien n'est appliqué. `assign_custom_gcodes` exige l'impression couche par couche (`ToolOrdering.cpp:1291`, `GCode.cpp:5043`).

### 1.6 Hauteur exacte ou numéro de couche [V-code + V-essai]

- Orca stocke une **hauteur** (`top_z`), qui correspond au haut de la première couche de la nouvelle couleur. L'interface ne manipule que des couches.
- **Piège vérifié** : avec une hauteur hors grille, les deux types ne tombent pas sur la même couche. Essai `off`, avec des couches de 0,48 et 0,56 :
  - une pause à 0,50 tombe sur la couche **0,48**, la plus proche ;
  - un ToolChange à 0,50 tombe sur la couche **0,56**, la première dont le haut est ≥ 0,50 (`ToolOrdering.cpp:732` contre `1321-1333`).
- Snap Studio devra donc toujours **caler les hauteurs sur les vraies couches** avant d'envoyer la liste.

### 1.7 Profils U1 officiels et firmware

**Profils [V-code]**

- `change_filament_gcode` (`P/Snapmaker U1 (0.4 nozzle).json:11`, identique pour les buses de 0,2, 0,6 et 0,8) :
  - relève Z de 1,5 mm ;
  - `M109 S<temp> T<n>` attend la chauffe de la tête suivante ;
  - `M400`, puis `T<n>` (prise de tête) ;
  - `SET_VELOCITY_LIMIT ACCEL=3000` si le filament est du PVA ;
  - `SM_PRINT_PREEXTRUDE_FILAMENT INDEX=<n>` si la tête n'est ni la précédente ni la tête initiale.
- `machine_pause_gcode` = **`M600`** (`P/Snapmaker U1 (0.4 nozzle).json:200`, `:199` pour les autres buses). Le parent `fdm_U1.json:181-182` contenait `M601` et un `change_filament_gcode` vide.
- `template_custom_gcode` n'est pas défini, donc Orca masque « Add Custom Template » (`IMSlider.cpp:1365`) [D pour l'effet].

**Firmware 2.0.0 [V-code]**

- `[gcode_macro M600]` appelle `PAUSE` (`lava/fluidd.cfg:63-65`). `M601` n'est défini nulle part dans `lava/`.
- `PAUSE` mène à `INNER_PAUSE` (`klippy/extras/pause_resume.py:85-108`) :
  - il mémorise la tête et les températures des 4 têtes ;
  - il rétracte ;
  - il monte de 5 mm et va à `MOVE_TO_DISCARD_FILAMENT_POSITION` (`fluidd.cfg:336-372`).
- Le firmware a aussi `SET_PAUSE_AT_LAYER LAYER=<n>` (`fluidd.cfg:627-660`). C'est une pause armée à la volée, côté imprimante.
- Après un `M600`, la sauvegarde de reprise après coupure de courant est coupée (`self.pl_allow_save_env = False`, `klippy/extras/virtual_sdcard.py:975-976`). L'effet exact reste à vérifier [D].

### 1.8 Essais sur le vrai moteur (Snapmaker Orca 2.4.0) [V-essai]

Conditions : plaque de 40 × 40 × 1,6 mm, profils U1 officiels aplatis, couches de 0,08 avec une première couche de 0,16 (réglage HueForge habituel), remplissage 100 %, 4 PLA de couleurs différentes.

| Essai | Entrée | Résultat |
|---|---|---|
| `none` | rien | 1 tête (3,37 g sur T0) |
| `json` | `--load-custom-gcodes` : ToolChange à 0,48 / 0,80 / 1,12, pause à 1,04 | couche 5 (Z 0,48) en `T1`, couche 9 en `T2`, couche 12 en `;PAUSE_PRINT` + `M600`, couche 13 en `T3` ; 4 têtes utilisées (0,88 / 0,67 / 0,67 / 1,17 g) ; +16 s estimées |
| `xml` | même liste dans `Metadata/custom_gcode_per_layer.xml` | G-code identique |
| `off` | pause et ToolChange à 0,50 | pause sur Z 0,48, `T1` sur Z 0,56 (cf. 1.6) |
| `tower` | `json` avec `enable_prime_tower=1` | changements identiques, tour imprimée, 15 min 10 s au lieu de 12 min 16 s |
| `mix` | ToolChange à 0,80 vers le filament 5 = tête virtuelle T0/T2 à 33 % | à partir de Z 0,80, alternance T2/T0 couche par couche |

D'autres effets sont visibles dans le G-code : la tête quittée est mise à 70 °C (`M104 S70 T0 ; cooldown`) et la suivante est attendue à 220 °C (`M109 S220 T1`).

### 1.9 Limites pour la U1 4 têtes (synthèse)

1. Sans intervention, il y a au plus **4 couleurs physiques**, plus des **têtes virtuelles** (mélanges de 2 têtes, vérifié). Au-delà, il faut des pauses : M600 → PAUSE, puis échange manuel d'une bobine.
2. Toute la plaque doit être imprimée par **un seul extrudeur** (mode `MultiAsSingle`). Un objet peint en plusieurs couleurs, deux objets sur deux têtes ou les **piliers de purge par matériau** de Snap Studio (des objets sur plusieurs têtes) empêchent la bascule. C'est vérifié dans le code (`ToolOrdering.cpp:457`) ; pour les piliers, c'est [D].
3. Pas d'impression objet par objet.
4. La pause n'affiche pas de message à l'écran (`extra` non émis), donc l'application doit dire elle-même quoi charger.
5. Chaque changement de tête attend la chauffe de la tête suivante, ce qui coûte du temps réel ; l'estimation n'en compte que peu [D].
6. Le `ColorChange` M600 « mono-tête » à la Prusa ne fait rien dans ce moteur.

## 3. Compatibilité HueForge

**Fichier « Describe » et instructions d'échange [S]**

- HueForge exporte un STL et un fichier texte « describe ».
- Exemples publics :
  - https://makerworld.com/en/models/2446092-the-two-of-us-hue-forge
  - https://makerworld.com/en/models/1344772-the-chosen-series-hueforge
  - https://offmodel.media/articles/hueforge-without-ams-bambu-studio/
- Contenu :
  - `Print at 100% infill with a layer height of 0.08mm with a base layer of 0.16mm`
  - une liste `#rrggbb PLA <marque> <nom> Transmission Distance: x` ;
  - `Swap Instructions: Start with Black`, puis `At layer #11 (0.96mm) swap to Bronze` … `swap to Yellow for the rest.`
- Sémantique vérifiée par le calcul sur ces exemples : la hauteur est le **haut de la couche n**, numérotée à partir de 1. On a z = base + (n−1) × couche, soit 0,16 + 10 × 0,08 = 0,96 pour la couche 11, et 0,16 + 9 × 0,08 = 0,88 pour la couche 10 (Zelda TotK, https://makerworld.com/en/models/185608). C'est exactement le `top_z` d'Orca, et le ToolChange à 0,48 imprime bien la couche 5 dans la nouvelle couleur [V-essai].
- Les guides demandent de **reprendre la même couche et la même première couche** que HueForge, sinon les hauteurs ne tombent pas sur de vraies couches (offmodel.media, cité ci-dessus).

**Module « 3MF Export » de HueForge (0.9.4 et plus) [S]**

- Sources : https://shop.thehueforge.com/pages/3mf-export-how-it-works et https://support.3mfexport.com/getting-started/overview/
- Il est vendu sur la boutique HueForge. Le prix n'a pas été vérifié.
- Il cible nommément **Snapmaker Orca / Snapmaker U1**.
- Il écrit `Metadata/custom_gcode_per_layer.xml` avec des **ToolChange** entre filaments chargés, et une **pause (`type="1"`) une couche avant** quand il faut un filament non chargé alors que tous les emplacements sont pris. Le nombre d'emplacements vient du profil (`extruder_offset` pour un changeur d'outils).
- Il écrit aussi `layer_height`, `initial_layer_print_height`, `filament_colour`, `filament_type` dans `project_settings.config`, et un `layer_config_ranges.xml` pour le HRM (base imprimée plus épaisse).
- Il prévient que les numéros de couche ne correspondent plus au describe à cause du HRM, mais que les **hauteurs** restent justes.

**Comment l'importer dans Snap Studio [D]**

1. **3MF HueForge ou Orca** : lire `custom_gcode_per_layer.xml` (même grammaire que `bbs_3mf.cpp:3108-3190`), les couleurs avec `project_filaments` (existant), et `layer_height` / `initial_layer_print_height` dans `project_settings.config`.
   - Les numéros `extruder` sont ceux du projet et doivent passer par la correspondance couleur → tête de Snap Studio.
   - Le HRM n'est pas géré : il faut le signaler et appliquer la couche fine partout, ce qui donne un résultat juste mais plus lent.
2. **STL + describe.txt** : analyser `layer height of X`, `base layer of Y`, les lignes `#hex …` et `Start with …` / `At layer #n (z mm) swap to … [for the rest]`. On peut aussi coller le texte dans un champ, car il est souvent dans la description MakerWorld.
   - Les noms des lignes d'échange se rapprochent des lignes `#hex` par nom de couleur.
   - La hauteur **mm** fait foi ; le n° de couche ne sert qu'à vérifier.
3. Dans les deux cas : imposer la couche et la première couche, le remplissage 100 % si le describe le dit, et caler chaque hauteur sur la couche réelle, avec un avertissement si l'écart dépasse 0,01 mm.

## 4. Deux propositions

Les deux propositions passent par **le moteur**, sans post-traitement du G-code. Le moteur sait déjà faire le ToolChange, la pause, la tour de purge, les températures, les poids par tête et l'estimation, ce qui est vérifié en 1.8.

Un post-traitement qui insérerait des `T<n>` serait fragile : pas de tour, pas de pré-extrusion, des statistiques fausses, des vérifications de bobine faussées. Il est **écarté**, sauf éventuellement pour une pause seule.

Le transport est identique dans les deux cas : un `custom_gcodes.json` dans le dossier de travail et l'option `--load-custom-gcodes`, avec `mode: "MultiAsSingle"`. Les deux propositions diffèrent par **où et quand** l'utilisateur décide, et par le traitement de plus de 4 couleurs.

### Proposition A — « Couleurs par hauteur » dans Préparer, planifiées avant la découpe

C'est la proposition centrée sur HueForge et sur les têtes de la U1.

**Parcours**

1. L'utilisateur ouvre un HueForge : un 3MF, ou un STL suivi de « Importer les instructions HueForge… » (fichier ou texte collé). Snap Studio détecte les changements et passe la plaque en mode **« Par hauteur »**, un 3e choix à côté de « Par objet / Par couleur » (`index.html:339-342`).
2. Une **règle de hauteur verticale** s'affiche à côté de la vue 3D de Préparer. Elle montre des bandes de couleur, et chaque bande porte une pastille de tête (T1 à T4, V1…).
   - Le modèle 3D est **teinté par tranches de Z** avant toute découpe. C'est le « vrai » aperçu HueForge, que ni Orca ni Bambu ne montrent avant la découpe.
3. Dans l'inspecteur, une section « Couleurs par hauteur » liste les changements : hauteur en mm, n° de couche, tête cible avec sa bobine réelle, et type « Automatique » ou « Pause ». On peut ajouter, déplacer (glisser sur la règle, avec calage magnétique sur les couches) ou supprimer.
4. Un **plan de bobines** est calculé automatiquement :
   - les 4 premières couleurs vont sur les têtes qui ont déjà la bonne bobine, d'après la couleur ΔE de `spoolcheck.js` ;
   - au-delà, Snap Studio ajoute lui-même une **pause** une couche avant, comme le module HueForge, et choisit quelle tête recharger (une tête qui ne resservira plus).
   - La feuille de découpe résume : « 6 couleurs : 4 automatiques, 1 pause à 1,04 mm pour charger Blanc sur T2. »
5. Pendant l'impression, Prints détecte que la pause en cours est **prévue** grâce au plan stocké dans le job. Une carte « Chargez Blanc sur T2, puis Reprendre » s'affiche, avec un bouton Reprendre. L'échange de bobine guidé n'est proposé que si le test U1 le permet (cf. §2, Contrôle).
6. Lors d'un départ depuis la file, la vérification des bobines contrôle les têtes du départ et rappelle les recharges prévues.

**Intégration UI**

- Préparer : mode « Par hauteur », règle verticale près de `p-canvas`, section dans `p-insp`.
- Feuille de découpe : résumé dans `s-map`.
- Aperçu : les bandes sont déjà visibles en mode Filaments ; on y ajoute des repères **en lecture seule** sur `v-layer`, avec une marque « pause ».
- Prints : carte de pause prévue.

**Modèle de données**

- `PR.heightChanges = [{ z, head, kind: "auto"|"pause", note? }]` dans la plaque, ses étapes d'annulation et sa sauvegarde.
- Dans le 3MF enregistré, écrire `Metadata/custom_gcode_per_layer.xml` au format Orca, donc relisible par Orca, plus un éventuel `snapstudio_colors.json` pour la note et le plan de bobines.
- Côté Rust : `Request.height_changes`, converti en `Info` JSON. Une tête physique h devient le filament h+1, une tête virtuelle k le filament n+k+1, une pause le type `PausePrint`.
- Le plan est recopié dans le job (`jobs.rs`).

**Slicing**

- Ajouter `--load-custom-gcodes`.
- Bloquer avec un message clair si la plaque a plus d'une tête par objet, des pièces peintes ou des piliers par matériau, ou si elle est en objet par objet.
- Compter les têtes des changements dans `prTowerHeads` et dans le contrôle « tête vide » (`slice.js:636-641`).
- Forcer couche et première couche depuis l'import.

**HueForge** : import 3MF et describe, calage des hauteurs, plan de bobines au-delà de 4.

**Avantages**

- Le flux HueForge le plus simple : ouvrir, vérifier, imprimer.
- Un aperçu en couleur **avant** la découpe.
- Exploite les 4 têtes et les têtes virtuelles sans intervention, et gère plus de 4 couleurs proprement.
- Les pauses sont expliquées à l'utilisateur, ce qu'Orca ne fait pas.
- Fichier compatible avec Orca dans les deux sens.

**Inconvénients**

- Le plus gros chantier : règle 3D, teinte par Z dans le moteur de rendu WebGL, plan de bobines, carte de pause.
- Il faut savoir calculer les couches avant la découpe. C'est simple tant que les couches sont uniformes ; le lissage des têtes virtuelles et le HRM ne sont pas gérés.

**Complexité et risque** : élevés. Le risque technique côté moteur est faible (vérifié). Les risques réels sont côté UI et côté U1 : comportement en pause, temps de chauffe, suintement des têtes en attente sans tour.

**Tests**

1. Tests unitaires : analyse du describe, lecture et écriture du XML, calage z → couche, plan de bobines (4, 5 et 8 couleurs), conversion tête → filament.
2. Test d'intégration `#[ignore]` sur le moteur, sur le modèle de `engine_virtual_head_alternates` (`slice.rs:2453-2530`) : vérifier que `T<n>` tombe au bon `;Z:` et que `;PAUSE_PRINT` est présent.
3. Sur une vraie U1 :
   - un HueForge 4 couleurs (100 × 100 mm, 0,08/0,16, 100 %), avec et sans tour, pour comparer suintement, alignement et temps réel contre estimé ;
   - un 6 couleurs avec pause : parcage, échange par l'écran puis par Snap Studio si c'est possible, reprise, absence de décalage de couche ;
   - une tête virtuelle comme cible ;
   - un départ depuis la file avec une bobine différente ;
   - une coupure ou une reprise après `M600`, pour voir l'effet de `pl_allow_save_env`.

### Proposition B — Repères sur la barre de couches de l'aperçu, façon Orca, puis nouvelle découpe

C'est la proposition générique, la plus proche d'Orca.

**Parcours**

1. L'utilisateur découpe normalement et ouvre l'aperçu.
2. L'ascenseur `v-layer` devient un ascenseur riche : graduations en mm, repères colorés, et un bouton « + » sur la couche choisie qui ouvre un menu :
   - « Changer de tête → T1…T4 / V1… » (pastilles avec la couleur des bobines) ;
   - « Pause (changer de bobine) » avec une note libre ;
   - « G-code personnalisé… », en mode avancé.
3. Chaque ajout relance la découpe en arrière-plan avec la liste, à la manière du bouton « Modifier les réglages » actuel, et l'aperçu se recolore.
4. Dans le panneau `v-panel`, une liste des repères permet d'éditer ou de supprimer, et « Importer des instructions HueForge » remplit la liste.

**Intégration UI** : uniquement la fenêtre d'aperçu (`viewer.js`, `index.html:1572-1600`), plus le résumé dans la feuille de découpe. Préparer ne change pas.

**Modèle de données**

- Les repères sont rattachés à la **découpe** (`SL.heightChanges`), avec `{ z, type, head, extra }`, ce qui correspond 1:1 à `CustomGCode::Item`.
- Ils sont retenus pour la plaque au moment de la sauvegarde (même XML qu'en A).

**Slicing** : même transport (`--load-custom-gcodes`). Le calage est naturel, puisque les repères sont posés sur des couches réelles déjà découpées (`layerZ`, `viewer.js:348-386`). `gcode.rs` doit apprendre `;PAUSE_PRINT` et `;CUSTOM_GCODE` pour les afficher.

**HueForge** : import de la liste dans l'aperçu, puis nouvelle découpe. La première découpe doit avoir la bonne hauteur de couche ; il faut donc soit un avertissement, soit l'imposer à l'import.

**Avantages**

- Chantier plus petit et localisé, sans rendu 3D par tranche avant découpe.
- Les repères sont toujours sur de vraies couches.
- Familier aux utilisateurs d'Orca et de Bambu, et ouvert à tous les usages : pause pour insérer un aimant ou un écrou, G-code perso.

**Inconvénients**

- Une découpe préalable est obligatoire, puis une nouvelle découpe à chaque modification : environ 10 à 60 s selon le modèle [D].
- Pas d'aperçu avant découpe.
- Le plan de bobines au-delà de 4 couleurs reste manuel, comme dans Orca ; l'utilisateur choisit où mettre les pauses.
- L'aperçu est une fenêtre de consultation, et y éditer change son rôle.

**Complexité et risque** : moyens. Le risque moteur est le même (faible). Il y a un risque UX : des nouvelles découpes à répétition et un état « aperçu obsolète » à gérer.

**Tests** : tests unitaires de la liste et de la conversion ; test moteur identique à A ; sur U1, les mêmes essais 4 couleurs et pause, plus une pause « aimant » sans changement de couleur.

### Comparaison rapide

| | A — Préparer, planifié | B — Aperçu, façon Orca |
|---|---|---|
| Aperçu avant découpe | oui, modèle teinté par Z | non |
| Plus de 4 couleurs | pauses et plan de bobines automatiques | pauses manuelles |
| Import HueForge | complet (3MF et describe), réglages imposés | liste importée, réglages à vérifier |
| Nouvelles découpes | 1 | 1 par modification |
| Usages hors HueForge (aimant, G-code perso) | possibles mais secondaires | naturels |
| Taille du chantier | grande | moyenne |

## 5. Recommandation

**A comme cible, livrée par étapes, en reprenant de B seulement les repères en lecture seule dans l'aperçu.**

1. **Étape 1 (socle commun).**
   - `Request.height_changes` et `--load-custom-gcodes`.
   - Calage sur les couches.
   - Blocages clairs : plusieurs têtes par objet, peinture, piliers, objet par objet.
   - Têtes des changements comptées pour la tour, les têtes vides et la vérification des bobines.
   - Lecture de `custom_gcode_per_layer.xml` à l'ouverture d'un 3MF (aujourd'hui perdu) et écriture dans `save_scene`.
   - `gcode.rs` lit `;PAUSE_PRINT`, et les repères s'affichent en lecture seule sur `v-layer`.
   - Test moteur.
2. **Étape 2.** Mode « Par hauteur » dans Préparer : liste dans l'inspecteur, règle verticale, import du describe HueForge, bandes de couleur dans la vue 3D.
3. **Étape 3.** Plus de 4 couleurs : plan de bobines, pause prévue une couche avant, carte « Chargez X sur Tn » dans Prints. L'échange guidé ne vient qu'après un test U1 sur `AUTO_FEEDING` en pause.

Raisons :

- Le moteur fait déjà tout le travail difficile, c'est vérifié sur la 2.4.0 et le code est identique en 2.4.1 (PR #86).
- La valeur propre à Snap Studio est l'aperçu avant découpe et le plan de bobines, qui exploitent les 4 têtes et les têtes virtuelles de la U1.
- Les deux points à valider sur une vraie U1 avant l'étape 3 :
  - la qualité sans tour : suintement des têtes en attente à 70 °C, pré-extrusion ;
  - le déroulé d'une pause `M600` avec échange de bobine et reprise.
